# AI 学习系统 v0.7 方向性预期

> 状态：Directional expectation，未批准开发<br>
> 文档版本：0.1<br>
> 预期版本：`v0.7.0`<br>
> 日期：2026-07-22<br>
> 前置条件：v0.6 完成 RC、至少 14 日受控观察和退出复盘<br>
> 决策来源：repository owner 选择 v0.6 方向 A，并要求未进入 v0.6 的 AI 深化能力纳入后续版本预期<br>

> **治理声明**：本文是候选池，不是活动实施计划，不授权提前修改代码、数据库或发布环境。v0.7 立项时只能选择一个产品主方向，其余能力继续保留为候选，不能把本文全部条目自动转为 Must。

## 1. 候选框架：无默认主方向

v0.7 当前没有默认主方向。“AI 知识连接与自适应扩展”只是用于整理候选能力的框架：在 v0.6 已证明问题、rubric、逐点评估和调度事件可信之后，再根据真实阻断选择跨卡片关系、更丰富输入、个性化调度、运行效率或修正闭环中的一个方向。

v0.7 的正式主题必须由 v0.6 数据决定：

- 如果主要问题是“用户会答题，但跨资料知识仍割裂”，优先概念图谱；
- 如果 FSRS shadow 明显改善校准和工作量模拟，评审正式调度切换；
- 如果主要阻力是图片、PDF 等资料无法进入系统，优先 Vision/多模态；
- 如果主要阻力是成本、延迟或 Provider 不稳定，优先模型路由与流式体验；
- 如果主要问题是 AI 错误无人处理，优先完整修正与重算闭环。

## 2. 候选能力池

### 2.1 Concept Graph 与跨卡片关系

候选能力：

- `concepts`、`claim_concept_links`、`concept_edges`；
- related / prerequisite / supports / contradicts 四类候选关系；
- 跨笔记相同概念聚合、孤立概念和知识缺口发现；
- 基于已确认关系的学习路径建议；
- 星图从数据血缘展示升级为语义洞察入口。

可信边界：

- AI 只能提出候选边，每条边必须带来源、证据、模型版本和 confidence；
- prerequisite 与 contradiction 默认需要人工确认；
- Embedding 相似不能等价为“原文有证据”；
- 概念合并、拆分、版本替换必须可撤销、可重算；
- 不允许 AI 关系覆盖 source → note → card → key point 的真实血缘。

### 2.2 FSRS 正式接管与个性化调度

进入正式立项的必要输入：

- v0.6 shadow 数据达到预先冻结的最小样本量；
- 离散策略与 shadow 预测能在同一事件语义下离线重放；
- 按预测 retrievability 分桶的真实回忆结果具有可接受校准；
- 工作量模拟、遗忘风险和异常边界都有报告；
- 维护库、算法版本、参数版本和回滚策略已锁定。

候选能力：

- 从 shadow 切换到 feature-flagged 正式 scheduler；
- 全局默认参数，数据充分后再评审个体参数优化；
- 普通 UI 只展示“为什么今天复习”，D/S/R 保留在诊断页；
- 版本升级使用新 decision 记录，不覆盖历史。

如果样本不足或收益不明确，FSRS 继续 shadow，不因版本排期强行转正。

### 2.3 Embedding 语义候选

候选用途：

- 长资料中的 evidence 候选召回；
- 概念和相似 claim 候选发现；
- 重复知识点与潜在矛盾的初筛。

边界：Embedding 只负责候选集合；hard evidence 仍需原文、block/version 和字符串级验证。向量索引不得成为唯一业务事实来源。

### 2.4 Vision 与多模态理解

候选能力：

- 对笔记 image block 做真实视觉理解，而不是只发送 alt text；
- PDF/截图/OCR 的页码、区域和版本化引用锚点；
- 图表、公式、流程图的题目与 evidence；
- 图片更新后下游题目、rubric 和验证结果的 stale 传播。

进入条件：选定一个垂直切片，不同时铺开 PDF、Office、OCR、网页快照和所有图片类型；对象存储、隐私同意、大小限制、删除与导出边界先闭环。

### 2.5 流式交互

候选能力：

- 问题准备、评估反馈和修复过程的可取消流式状态；
- 断线恢复与后台完成通知；
- 首 token、完整结果和取消率指标。

流式只改善感知等待，不计作“AI 更聪明”。结构化最终结果仍须通过完整 schema 后才能产生业务副作用。

### 2.6 多模型路由

候选能力：

- 按任务选择卡片生成、出题、评估或视觉模型；
- Provider 健康、成本和质量驱动的显式路由；
- fallback、熔断、预算和 user/workspace policy。

进入条件：v0.6 已有分任务质量集、token/成本和延迟统计。不得在没有同一黄金集对比时以模型价格或主观印象自动切换 Provider；不得越过用户的 BYOK 与隐私选择。

### 2.7 完整结构化反馈与可重算

候选能力：

- 用户针对题目、rubric、逐点评估、证据和学习卡提交结构化问题；
- 处理状态、Owner 分流、修正提案与审计；
- 修正后使下游问题、评估、schedule 或图谱关系 stale；
- 从事实记录安全重算派生结果；
- 可用于质量改进的去内容化统计与受控人工标签流程。

v0.6 只保留轻量的“判定有问题”信号和安全影响控制，不建设完整工单后台。

### 2.8 更丰富题型与自适应题库

候选能力：

- 同一 key point 的多题变体与近期去重；
- 根据历史逐点评估选择 explanation / transfer / boundary 难度；
- 排序、填空、选择与判断等新增题型；compare/diagnose 仅在 v0.6 Should 未交付时由本候选承接，若已交付则只做其多题变体和难度自适应；
- 代码题的可执行测试、资源隔离与安全沙箱。

边界：选择题和判断题不能替代主动回忆；没有执行器的代码题不得用文本相似度伪装成正确性判断。

## 3. v0.7 立项选择规则

v0.6 退出复盘后，按以下顺序选择一个主方向：

1. 用户价值阻断程度；
2. 是否有足够真实数据定义验收门槛；
3. 是否复用 v0.6 的可信事实和质量门禁；
4. 安全、隐私和可回滚性；
5. 成本与单人维护能力。

概念图谱、Vision 和多模型路由不得同时作为 Must。FSRS 转正属于独立 go/no-go 决策，即使选择其他产品主方向也可以继续 shadow。

## 4. 持续门禁，不得推迟到 v0.7

以下不是“未来功能”，而是每个版本都必须持续满足的基础约束：

- RLS、workspace/user 隔离与受限数据库角色；
- migration fresh/upgrade/restore；
- 回答正文、题目、证据和 Provider 响应的遥测隐私边界；
- Worker lease、幂等、重试和无重复业务副作用；
- 390 / 768 / 1440 三视口、键盘、WCAG 与错误恢复；
- 真实 Provider 质量门禁、成本上限和发布追溯；
- 备份、恢复、灰度与回滚。

## 5. v0.7 正式立项前必须回答的问题

- v0.6 中哪一个用户阻断最常出现，分子、分母和观察周期是什么？
- 问题生成、评估与卡片修复的质量基线是否稳定？
- FSRS shadow 是否有足够数据，还是仍为 `insufficient_data`？
- 资料中图片/PDF 的真实占比是否足以支持多模态投入？
- 概念关系的人工确认率和撤销率能否定义？
- Provider 成本与延迟是否真的需要路由，而不是先修任务流程？
- 哪些候选应明确继续后延，而不是塞入一个版本？
