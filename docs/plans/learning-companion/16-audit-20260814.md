## 3. 桌面端真实缺口 ❌（按优先级）

### 3.1 最高：Journey V2 桌宠首邀前端 = 0 接线 → 新用户引导真空

- Pet 窗口页面（`/companion/pet`）**不消费** `/companion/journey/bootstrap`、`/companion/invitation/actions`、
  `/companion/journeys/:id/actions`（全仓库 web 代码零调用）；
- `PetJourneyPresentation` / `PetJourneyRedrawLab` 只挂在 `(prototype)/companion/pet/ui-redraw`；
- Electron 主进程无任何 onboarding / invitation 逻辑；
- 同时 `apps/web/lib/home-onboarding.ts` 在 journey flag 打开时**直接禁用首页 onboarding 大卡**（`showOnboarding:false`）。
- **净效果：桌面端新用户既看不到首页引导，也收不到桌宠首邀，首次引导是断的。**

### 3.2 Bridge 无页面调用方（§14.6 Context Adapter 全部未实现）

- `publishPageContext / renewPageContext / revokePageContext` 在 preload 定义处之外**无任何调用**；
- Home/Today/Source/Note/Card/Review/Player/Star Map/History 的 Context Adapter 一个都没接；
- "桌宠自动知道用户当前在哪张卡/哪道题/哪颗星"不成立；Pet turn 不携带 `AssistantContextSnapshotV2`。

### 3.3 durable delivery 无消费方 → 主动 cue 一条都出不来

- 后端 inbox SSE（`/companion/deliveries/inbox/stream`）、timeline、display lease、policy engine 齐备，
  但 Pet 不订阅、不 ACK、不渲染；deliveries 状态永远停在 `delivered` 之前。

### 3.4 记忆：后端 service 存在，无路由、无 UI

- `memory-service.ts` 仅内部使用；无 HTTP 端点、无候选确认 UI、无删除入口（方案 16 §10.3）。

### 3.5 历史页导出 / 删除 / 召回桌宠 = disabled 待接线

- 服务端 export / delete API 已存在；UI 三个按钮仍 `disabled`（"待接线"）。

### 3.6 Pet 学习动作仍是旧 proposal 协议

- `learning-actions.ts` 走旧 `/api/companion/learning-context` + `createMenuProposal`
  （`candidateId: resume_current / start_short`，learning-action-bridge），
  未切方案 16 §18 的 Assistant Orchestrator proposal / ActionRun 体系；
- 桌宠发起的 LearningRun typed proposal 闭环（确认 → 执行 → 真实回执 → 收尾）未接。

### 3.7 P1：注册后主动创建 Pet 窗口未接

- Electron 主进程仅在 `petModeEnabled` / spike / 托盘点击时创建窗口；
- 没有 `session.ready(newUser=true)` 驱动的"Pet 不存在则创建"路径。

### 3.8 P4：结构化任务上限

- live 链路缺省只生成 text/voice；structured 仅 `star_map + goal=repair` 触发，且无 qualification 数据恒 `practice_only`；
- choice / scenario renderer 在 live 链路 fail closed（§7.7 V1 上限）。

### 3.9 P7：星图主渲染未切流 + 本地视口快照未实现

- graph 主图仍走旧 reader（flag 只开了投影同步与 delta 显影）；
- `LocalGraphViewportSnapshotV1`（runId 绑定、设备本地视口恢复）未实现。

### 3.10 P9：旧栈未删除（`cards/[id]/companion` 路由是唯一已删项）

- `ValidationFocus`、`cards/[id]/validate`、`review/[scheduleId]`、旧 `/graph` reader、
  旧 permit-based proactive deliveries、localStorage dialogue fallback 均仍在；
- 删除须按 19 号记录 §9.12 的 runbook 与 Gate 条件（E03/E04/E12/E16/E10/E11/E14）执行。

## 32. 十六次回审（2026-08-15）：worker 容器崩溃（任务全失败）专项

> 用户反馈"worker 容器没重构，好多任务失败"。定位为 **dev 栈 worker 容器
> 崩溃循环**（tsx watch 每次 rerun 即崩，约 22h 内全部任务失败），非镜像
> 陈旧。

### 32.1 症状与定位过程

- `docker logs ailearn-dev-worker-1`：`SyntaxError: The requested module
  '../schema/index.ts' does not provide an export named 'cardGenerationPlans'`
  （plan-repository.ts:4），tsx watch 崩溃后等待下一次 change，任务零处理；
- 宿主机构建链（`npx tsc`/web 测试）全绿，schema 导出正常——差异仅在容器；
- 逐层 probe（容器内 `npx tsx` import）：
  - 直接 import `/apps/api/src/db/schema/index.ts` → 命名空间**仅 1 个导出**
    （宿主机 144 个）；
  - worker 转发层 → 0 个导出；
  - `--preserve-symlinks` 下 `@ailearn/shared`（symlink）目标缺失 → 需挂
    /packages/shared 及其 zod/ts-fsrs。

### 32.2 根因（三要素，最终修复 = docker-compose 挂载补齐）

worker 服务此前只挂载 `./apps/api/src:/apps/api/src`，导致：

1. **`/apps/api/package.json` 缺失（主因）**——宿主机 `apps/api/package.json`
   声明 `"type": "module"`，容器里 /apps/api 无该文件 → Node/tsx 把 api 的
   .ts 全部按 **CJS** 转译 → esbuild CJS 模式下嵌套 `export *` 转发链丢失
   （`__exportStar` 空命名空间）→ `cardGenerationPlans` 等全部导出不可见 →
   SyntaxError。**任何 tsx 版本（4.23.1/4.23.12）与任何加载器（tsx CLI /
   node --import tsx）均复现**；
2. `/apps/api/node_modules` 缺失——schema 文件裸 import `drizzle-orm` 按文件
   位置向上解析失败（此前依赖 tsx 入口前缀缓存的非标准行为）；
3. `@ailearn/shared` 为 symlink（api node_modules 内，install-links 未打包），
   `NODE_OPTIONS=--preserve-symlinks` 下需目标 `/packages/shared` 与其自带
   zod/ts-fsrs 可见。

### 32.3 修复（docker-compose.dev.yml worker volumes，4 行挂载）

```yaml
- ./apps/api/package.json:/apps/api/package.json:ro   # type: module 声明
- ./apps/api/node_modules:/apps/api/node_modules       # drizzle 标准解析
- ./packages/shared:/packages/shared                   # @ailearn/shared symlink 目标
- ./packages/shared/node_modules:/packages/shared/node_modules  # zod/ts-fsrs
```

`docker compose -f docker-compose.dev.yml up -d --no-deps worker` 后日志恢复
正常消费：`companion_dialogue` 等任务开始处理（报 AI consent 未签署属正常
业务拒绝，非崩溃）。

### 32.4 备注

- 容器内临时 `npm install --no-save tsx@4.23.12` 验证过非版本问题，recreate
  后回滚镜像层 4.23.1 亦正常——**根因与 tsx 版本无关**；
- worker 包既有 typecheck 错误（evidence-persist.ts）仍为独立既有项

### 32.5 补记：reaped jobs 恢复逻辑参数绑定 bug（崩溃掩盖的第二处）

崩溃修复后启动恢复逻辑仍报 `failed to load reaped jobs for generation
projection`（每 60s，projectedJobs 为 0）。逐层 probe 定位：

### 33.2 框架在、无闭环（用户不可见）

1. **Journey 首次引导**：PetJourneyLive（13 步）+ reducer + 服务端 journey-service
   全在，**前端零挂载**（pet 页只渲染 PetSurface）→ 引导永不出现；
2. **主动 delivery 层**：PetDeliveryLayer / DeltaReceiptNotice / delivery-client
   （lease/ack/stream）全在，**零挂载**；服务端 `deliver()` 唯一产生方 =
   run.completed system_event（proactive-hook），`delivery-service.ts` 通用
   写入**零调用**；proposal / action_result / proactive_cue / message
   **零产生方**（Orchestrator 未接线，同 §29.3 标注）；
3. **工具网关（15 kind）**：API + 同步执行完备，**生产代码零调用**
   （仅 integration-tests 直调）→ 桌宠没有任何学习动作入口；
4. **V2 bridge 业务消费为零**：`usePetBridgeContext()` 唯一消费者是未挂载的
   DeltaReceiptNotice；`dispatchOpenRoute`/`dispatchInPageCommand`
   **零调用**（PetMenu 导航仍走本地 reducer dispatch）；`publishUiEvent`
   业务调用为零（graph.delta_applied 等回执发射方不存在）；

### 33.3 批次记录与实际脱节（此前总结失实处）

- 声称"Pet 端 in-page 命令 + command 回执"——实际零调用；

  PetDeliveryLayer/DeltaReceiptNotice；

### 33.4 结论

方案 16 的"框架层"（合同、组件、API、投影、bridge、埋点、桌面窗口）大量
落地并可用；**"主动体验层"（引导、提议、提醒、结果收尾展示）是真实缺口**，
用户看到"桌宠只有聊天"是准确现状。补齐需：前端挂载 Journey/delivery 层 +
服务端产生方接线（Orchestrator 节点）+ 工具入口闭环 + 主窗口事件接入
（review/cards/graph 等），属后续实施批次，工作量明确。
