## 1. 审计口径与结论

本轮在 macOS Electron 开发窗口、当前共享开发库和 API/worker 容器上操作。源码基点 `5857ab16`，工作树已有大量其他未提交改动；本文只新增审计文档。使用 Personal Beta 演示空间做只读页面检查和安全退出/暂停操作；为核对复习资格，启动过一条复习 run，并在未输入、未提交答案时暂停。没有创建、删除、归档来源或笔记，也没有生成新卡、完成/延后复习。

**最影响使用的是两类问题叠加：**

1. 启动/运行时门禁会反复回到“正在刷新状态”，实机两次复现，第二次持续数分钟后自行恢复。API `/health`、`/ready` 同时为 200。首页“恢复学习旅程”还出现过任务区超过 15 秒空白、run 详情却已 200 的情况。用户可能暂时连笔记、今日学习、搜索、设置或未完旅程都走不到。
2. 首页承诺“10 项可恢复”却把人带到没有恢复列表的今日日志。即便进入理解目标，用户看到“练过了”却是 `0 次练习`，又同时看到“正式验证还没安排”“当前旅程等待下一步”“复习安排已经到期”。到复习队列时，同一目标的多张卡标题和来源完全一样；一张显示“开始复习”的到期卡实际只能进行不推进排程的练习。**缺少一个清楚、可执行、解释缘由的下一步**，这是“用起来怪”的主要产品原因。

另有一条确定的服务端故障：`GET /v2/card-generation-runs/active` 返回 500，使“恢复未完成的生成”无法可靠显示。伴星 AI 审计写入在受限 worker 数据库角色下失败，属于可追溯性缺陷。

### 1.1 第二轮补完写入型链路后的结论

第二轮在同一个演示空间把上一轮标为“未执行”的写入型终点逐个点完（提交作答、补充证据、结束一轮、稍后提醒、采集新来源、生成邀请），并同步读 API/worker 日志与库侧行。四条结论：

1. **采集链路当前完全不通（F27）。** 粘贴一段文本提交后，来源永久停在“待解析 / 正在解析”，详情页的“开始写笔记”因此永久禁用；服务端那条 `parse_source` job 三次重试后 `dead`，真因是 worker 起手读来源时没有工作区上下文，被 `sources` 的租户策略挡成“查不到”。库侧时间线显示该空间最后一次解析成功是 2026-09-22 04:33，此后第一条（就是本轮这条）即失败——也就是说这条链路已经断了一天而无人看见，因为界面把它显示成“还在排队”。
2. **复习与正式验证当前结不了算（F28）。** 从队列点“开始复习”，提交一段实质回答后 39 毫秒就得到 `not_assessable`（`rubric_results` 为空，根本没调用模型），日志两次给出同一句 `task rubric has no frozen evidence`。“继续补充证据”把用户引向第二次同样的失败，之后按钮消失，只剩“结束但不改变复习”。回到队列，画面与四分钟前逐字相同。系统缺的是**自己那侧的原文证据**，界面却把它说成“这一次判不出结论”，用户会以为是自己的回答不够好。
3. **上一轮的判断有两条需要修正。** F17 不只是“个人空间不该出现邀请按钮”——点下去确实会拿到 409，但界面把它翻译成“这条学习状态已经发生变化，请先同步后再继续”（F31），错误码在网关被折掉了；F23 的“只能练习”之外还叠着 F28 的“永远判不出”，两者共同导致到期卡无论怎么做都不推进排程。
4. **笔记这条链路断在“定版”那一步（F35/F36）。** 新建笔记 → 改标题 → 写两段正文 → 界面“● 已自动保存”，但库侧 `note_versions` 始终只有创建时那个**空的 v1**，`notes.title` 也仍是“无标题笔记”。详情面约 7 分钟后能显示正文（读的是未定版的实时文档），却在这一屏上标着“不可变版本：v1”；同一时刻列表卡写“版本 v1 · 1 段正文”又写“这一版还没有正文段落”。**两个面各读一套，标签与实际来源不符。** 而唯一定版的两条路都不可达：提示语让用户去点一个界面上不存在的“提交并确认”按钮，真正的“立即保存”与 ⌘S 都挂在 `dirty` 上，自动保存在 1.2 秒内就把 `dirty` 清掉（`notebook-surface.tsx:547` 直接 return，无任何提示）。**“版本历史 + 恢复切回那一版”这项能力，用户在正常写作节奏下一次都触达不到**；“用已经存好的整篇版本生成学习卡”拿到的也就是那个空 v1。

同时撤回一条中途产生的错误怀疑：作答页计时器长时间显示 `00:00 / 已暂停计时` **不是缺陷**——`learning-run-surface.tsx:328` 明确在窗口失焦时停走，而本轮由后台代理操作，窗口始终不是钥匙窗口。同一条也解释了一次“点首页导航没跳走”：失焦窗口的第一次无障碍点击会被 macOS 吞掉，重发即正常。这两点记在 §6 的量测限制里，避免下一轮再当成 bug 追。

### 证据等级

- **实机**：在 Electron 窗口看见并操作到的状态。
- **接口/日志**：直接请求本地服务，或查看运行中的 API/worker 日志、只读数据库统计。
- **代码可证**：当前调用路径足以证明后果，但本轮未在对应窗口完成点击复现。
- **待复测**：存在强烈风险或已在旧审计提出，但本轮条件不足以确认实际影响。

## 3. 问题清单和解决方案

优先级：P0 = 阻断核心链路；P1 = 核心任务常见错误或严重误导；P2 = 重要边界/性能/质量；P3 = 文案或局部体验。

### F01 · P0 · 门禁反复刷新，整个 App 可被卡住

- **证据**：实机两次进入“正在刷新状态 / 连接恢复后会自动继续 / 正在同步最新状态”，一次重启才恢复，第二次持续数分钟后自行恢复；当时 `/health`、`/ready` 为 200，约 10ms/5ms。API 日志近 1 小时约 1047 次 `/auth/me`，远高于正常用户操作量。
- **高可信代码原因**：`apps/desktop-client/src/renderer/src/components/DesktopAccessGate.tsx:976-1000` 的 runtime 订阅收到非断线事件也直接 `invalidateReadyGate()`；`apps/desktop-client/src/main/desktop-ipc.ts:1257` 将收件箱投递发成 `companion_activity_changed`，而 `home-projection.tsx:54-59` 本就能局部消费它。门禁的 `invalidateReadyGate()`（约 875 行）还会清理工作区视图并重新 bootstrap。这个事件不应该等同会话/空间失效。日志频率与之吻合，但持续刷新是否还有第二因素，修复时须用事件跟踪确认。

### F43 · P0 · 解散协作空间必然失败：记忆改指个人空间时撞唯一索引，整个事务回滚

- **证据等级**：实机端到端 + postgres 日志精确到键 + 回滚事务里的反证。实机路径：灵动岛空间菜单 → 新建“审计解散夹具 0923”（自动进入）→ 笔记里新建一篇并自动保存 → 来源里采集一段文本 → 设置 → 账户与空间 → “解散 审计解散夹具 0923” → 输入空间名（“确认解散”从 disabled 变可点）→ 点下。服务端 `DELETE /workspaces/79832399-…` 返回 **500，44ms**。postgres 日志给出完整因果：`duplicate key value violates unique constraint "assistant_memory_items_content_unique_idx"`，`Key (workspace_id, user_id, kind, source_event_id)=(Personal Beta, f6c4a80e…, preference, memory-extract:9b78bf30-…:0) already exists`，`CONTEXT: UPDATE public.assistant_memory_items m SET workspace_id = u.personal_workspace_id …`，`PL/pgSQL function ailearn_dissolve_workspace(uuid,uuid) line 52`。事后核对：空间、笔记、来源全部还在——**事务整体回滚，什么都没发生**。
- **根因是两件事叠加**：① 伴星的 global 记忆**按空间扇出**——同一批 10 条记忆带着**完全相同的 `source_event_id`** 同时存在于这个账号的 4 个空间里（Personal Beta / 21312 / 验收空间 acc0921 / 夹具空间各 10 条）；② `apps/api/src/db/migrations/0276_dissolve_workspace_function.sql:78-86` 的 re-home 是一条裸 `UPDATE … SET workspace_id = personal`，既没有 `ON CONFLICT`/合并，也不筛 `deleted_at`。于是**只要用户在两个以上空间被提取过同一条记忆（这是常态），解散就 100% 撞那个唯一索引**。
- **反证（在 `BEGIN … ROLLBACK` 里跑真函数，库里不留任何东西）**：先把夹具空间那 10 条记忆删掉再调 `ailearn_dissolve_workspace` → 函数返回成功，**102 张带 `workspace_id` 的表全部归零**、`workspaces` 父行被删、tombstone 正确落在发起者个人空间的 `workspace_audit_log`（4 → 5 行），随后回滚，复查库里一切如旧。**结论：逐表级联清理本身是对的、可用的；坏的只有“记忆改指个人空间”这一步。**
- **方案**：re-home 改成幂等合并——目标已存在同 `(user_id, kind, source_event_id)` 时丢弃源行（`ON CONFLICT DO NOTHING` 后删掉未搬动的，或先按目标键反连接删除再 UPDATE），并给这条 UPDATE 补 `deleted_at IS NULL`；更根本的是取消记忆按空间扇出（F44）。把本轮这段“回滚事务里对拍 102 张表”固化成一条测试，防止以后新增表又漏清。
- **验收**：多空间账号解散任意协作空间成功；解散后个人空间记忆条数不增不减（re-home 变成合并）；102 张表零残留由测试守住；失败时不再回滚成“什么都没发生但用户以为成功了”。

## 4. 理解目标 → 复习：建议重排的产品合同


当前页面把**目标状态、某次 run、正式证据、卡片排程**放在同一平面上，且进度词使用“练过了/说清了”等结果语气。多个卡片属于同一目标时，复习队列又只显示目标标题，用户既不知道“现在做哪件”，也不知道“做完这件会改变什么”。

建议把用户可见流程固定为四步：

1. **材料与笔记**：从哪份材料形成了哪篇笔记，原文证据是否齐全。
2. **学习卡**：生成状态、候选要审什么、激活后有哪些卡，每张卡考什么。
3. **理解目标**：此目标当前的正式证据是什么；正在进行的是哪一轮作答。只给一个主按钮，如“继续第 2 题”，旁边解释“上次暂无法判定，需要补充 X”。
4. **复习**：按目标归组，显示该组共几张卡、各卡差别、今天先做哪张及原因；开始前区分“可正式结算”和“只能练习”，完成一张后立即说明目标状态与剩余排程如何变化。

目标简报的推荐结构：顶部“**你现在要做：继续补充证据（第 2/3 题）**”；其下独立三行“本轮作答：进行中”“正式证据：尚无可判定结论”“今天到期：2 张卡（来自此前激活的卡）”。进度条只表示**已完成**的步骤，不把“已经开始”算作“练过”。复习卡应有唯一可读名称，例如“轨道周期的因果解释 · 第 4 轮”，而不只重复“Earth's orbital period”。

服务端应提供一份可审计的 `nextAction`（动作、对象 ID、原因、阻断原因），首页、目标详情、今日学习和复习入口都按它展示，不各自猜下一步。并建立状态矩阵：新目标、只有练习、正式验证部分完成、暂不可判、已证明但待复习、同目标多卡到期、复习前曝光导致只能练习、材料过时、卡撤回。每一格明确唯一主操作、次级操作、返回目标和完成后的用户可见变化。

第二轮补完写入型链路后，这份合同要加一条**前置条件**，否则上面四步的第 2–4 步在真实数据上根本走不到：**一个目标只有在“每个必选评分点都有冻结证据”时才可以被激活成卡并进入复习**（F28）。当前实现把这条判断留在结算时刻，于是用户一路被允许走到“提交 → 判不出 → 补充 → 又判不出 → 结束但不改变复习”，队列回到原样，看起来像产品在原地打转。同理，材料侧要加一条：**采集失败必须表现为失败**（F27），否则第 1 步就断了却显示成“还在排队”，后面的笔记、卡、目标全都无从产生。这两条修好后，F03/F04/F06/F23/F24 的文案与入口收敛才有可验证的落点——否则状态矩阵里“暂不可判”那一格实际上吞掉了两种完全不同的原因。

## 5.2 量测限制（下一轮先读这段，避免把方法问题记成产品缺陷）

- **后台代理操作时窗口不是钥匙窗口**：作答页计时器恒显 `00:00 / 已暂停计时` 是 `learning-run-surface.tsx:328` 的既定行为（失焦即停走，与服务端 activity lease 同规则），**不是缺陷**；同理第一次无障碍点击可能被 macOS 吞掉（本轮“点首页导航未跳走”重发即正常）。凡是“点了没反应”，先重发一次并读 `focused UI element` 是否落在被点元素上，再判断是否产品问题。
- **首页场景的无障碍树在动**：书桌热点展开/收起与空闲动画会让元素序号在捕获与点击之间失效（本轮出现 `Could not read the element's accessibility actions`）。F24/F26 的第二轮复测因此**未得结论**，仍以上一轮实机记录为准，不要引用本轮。
- **按关键词过滤无障碍文本会漏判**：本轮先用“个人空间/失败/错误”过滤，据此差点记一条“点击生成邀请完全无反馈”的假发现；截图显示红字提示其实在“工作区成员”下方。拒绝类结论必须用整屏文本或截图复核一次。
- **`typeText` 打不进中文到 contenteditable，别把它当"用户打字"**：向笔记正文 `typeText` 两段中文，结果只剩 `：。\n：。`——全角标点进去了、汉字全丢，长得完全像"编辑器吞字"。改用 `setValue` 后整句正常进入并自动保存。**结论：富文本/可编辑区一律先 `setValue`，`typeText` 只用于 ASCII 单字符探针。**
- **但 `super+键` 是能送达的，这条正控让 F36 的键盘证据成立**：同一个 `onEditorKeyDown` 里的 ⌘K 实测生效（光标停在“y”上按 ⌘K，正文出现 `[y](https:)`），所以随后 ⌘S 不产生版本不能归给"按键没到"，只能归给 `save()` 里那道 `!dirty` 的 return。凡是"某个快捷键没反应"，先在**同一处代码的另一条分支**上做一次能观察到的操作，再决定是不是产品问题。
- **共享库里的夹具数据会伪装成产品规模**：`learning_objective_revisions_v2` 有 186/237 行 `scoring_rubric` 是 JSON 字符串标量（双重编码），来自 `apps/api/src/integration-tests/helpers/v2-card-fixture.ts:121` 一类测试夹具，全部落在 `ws-*`、`domain-events` 等一次性空间；演示空间 Personal Beta 的 17 行都是正常对象。据此算出的“177 张卡没有 rubric”是**夹具污染**，不是产品缺陷——但值得单独处理（见 §7）。
- **无障碍树会给出与 DOM 相反的读数，所以“界面自己关了”这类否定结论必须两把尺一起量**（第三轮）：同一时刻无障碍树列得出空间面板里的“新协作空间名称”输入框，而只读 DOM 查询说那个输入框不存在。此前我据此差点把“空间菜单画不出来”记成缺陷（其实面板早就关了，是树在滞后）。**规则：凡是“某个东西消失了/没出现”，用只读 DOM 查询复核一次；两边不一致时按“我没读到”处理，不按“它没发生”处理。** 这条直接导致 F52 只列待核不列发现。
- **元素序号在弹层上尤其不可靠**：空间菜单、便签表单这类浮层的 `elementIndex` 在“捕获→点击”之间反复报 `Could not read the element's accessibility actions`，坐标点击又实测落到了相邻的另一行（想点“验收空间 acc0921”，点进了“21312”）。**规则：弹层里的目标要在点击前重新捕获、点完立刻用库侧或 DOM 读数验收落点，不能拿“屏上标签变了”当已生效。**
- **测试夹具里的假形状会把真缺陷埋进假失败**（第三轮，F02 验证现场）：`seedRun` 把哈希位写成 `"h"`，而合同是 `/^[0-9a-f]{64}$/`；新加的投影用例第一次**因为假形状而红**，报出来的正是“投影层解析失败”——和它要测的那个 500 长得一模一样。凡是新用例先红，先怀疑夹具的返回值是否符合服务端合同，再怀疑实现。
