## 1. 审计口径与结论

本轮在 macOS Electron 开发窗口、当前共享开发库和 API/worker 容器上操作。源码基点 `5857ab16`，工作树已有大量其他未提交改动；本文只新增审计文档。使用 Personal Beta 演示空间做只读页面检查和安全退出/暂停操作；为核对复习资格，启动过一条复习 run，并在未输入、未提交答案时暂停。没有创建、删除、归档来源或笔记，也没有生成新卡、完成/延后复习。

**最影响使用的是两类问题叠加：**

1. 启动/运行时门禁会反复回到“正在刷新状态”，实机两次复现，第二次持续数分钟后自行恢复。API `/health`、`/ready` 同时为 200。首页“恢复学习旅程”还出现过任务区超过 15 秒空白、run 详情却已 200 的情况。用户可能暂时连笔记、今日学习、搜索、设置或未完旅程都走不到。
2. 首页承诺“10 项可恢复”却把人带到没有恢复列表的今日日志。即便进入理解目标，用户看到“练过了”却是 `0 次练习`，又同时看到“正式验证还没安排”“当前旅程等待下一步”“复习安排已经到期”。到复习队列时，同一目标的多张卡标题和来源完全一样；一张显示“开始复习”的到期卡实际只能进行不推进排程的练习。**缺少一个清楚、可执行、解释缘由的下一步**，这是“用起来怪”的主要产品原因。

另有一条确定的服务端故障：`GET /v2/card-generation-runs/active` 返回 500，使“恢复未完成的生成”无法可靠显示。伴星 AI 审计写入在受限 worker 数据库角色下失败，属于可追溯性缺陷。

### 1.1 第二轮补完写入型链路后的结论

第二轮在同一个演示空间把上一轮标为“未执行”的写入型终点逐个点完（提交作答、补充证据、结束一轮、稍后提醒、采集新来源、生成邀请），并同步读 API/worker 日志与库侧行。三条结论：

1. **采集链路当前完全不通（F27）。** 粘贴一段文本提交后，来源永久停在“待解析 / 正在解析”，详情页的“开始写笔记”因此永久禁用；服务端那条 `parse_source` job 三次重试后 `dead`，真因是 worker 起手读来源时没有工作区上下文，被 `sources` 的租户策略挡成“查不到”。库侧时间线显示该空间最后一次解析成功是 2026-09-22 04:33，此后第一条（就是本轮这条）即失败——也就是说这条链路已经断了一天而无人看见，因为界面把它显示成“还在排队”。
2. **复习与正式验证当前结不了算（F28）。** 从队列点“开始复习”，提交一段实质回答后 39 毫秒就得到 `not_assessable`（`rubric_results` 为空，根本没调用模型），日志两次给出同一句 `task rubric has no frozen evidence`。“继续补充证据”把用户引向第二次同样的失败，之后按钮消失，只剩“结束但不改变复习”。回到队列，画面与四分钟前逐字相同。系统缺的是**自己那侧的原文证据**，界面却把它说成“这一次判不出结论”，用户会以为是自己的回答不够好。
3. **上一轮的判断有两条需要修正。** F17 不只是“个人空间不该出现邀请按钮”——点下去确实会拿到 409，但界面把它翻译成“这条学习状态已经发生变化，请先同步后再继续”（F31），错误码在网关被折掉了；F23 的“只能练习”之外还叠着 F28 的“永远判不出”，两者共同导致到期卡无论怎么做都不推进排程。

同时撤回一条中途产生的错误怀疑：作答页计时器长时间显示 `00:00 / 已暂停计时` **不是缺陷**——`learning-run-surface.tsx:328` 明确在窗口失焦时停走，而本轮由后台代理操作，窗口始终不是钥匙窗口。同一条也解释了一次“点首页导航没跳走”：失焦窗口的第一次无障碍点击会被 macOS 吞掉，重发即正常。这两点记在 §6 的量测限制里，避免下一轮再当成 bug 追。

### 证据等级

- **实机**：在 Electron 窗口看见并操作到的状态。
- **接口/日志**：直接请求本地服务，或查看运行中的 API/worker 日志、只读数据库统计。
- **代码可证**：当前调用路径足以证明后果，但本轮未在对应窗口完成点击复现。
- **待复测**：存在强烈风险或已在旧审计提出，但本轮条件不足以确认实际影响。

## 3. 问题清单和解决方案

优先级：P0 = 阻断核心链路；P1 = 核心任务常见错误或严重误导；P2 = 重要边界/性能/质量；P3 = 文案或局部体验。

### F01 · P0 · 门禁反复刷新，整个 App 可被卡住

- **证据**：实机两次进入“正在刷新状态 / 连接恢复后会自动继续 / 正在同步最新状态”，一次重启才恢复，第二次持续数分钟后自行恢复；当时 `/health`、`/ready` 为 200，约 10ms/5ms。API 日志近 1 小时约 1047 次 `/auth/me`，远高于正常用户操作量。
- **高可信代码原因**：`apps/desktop-client/src/renderer/src/components/DesktopAccessGate.tsx:976-1000` 的 runtime 订阅收到非断线事件也直接 `invalidateReadyGate()`；`apps/desktop-client/src/main/desktop-ipc.ts:1257` 将收件箱投递发成 `companion_activity_changed`，而 `home-projection.tsx:54-59` 本就能局部消费它。门禁的 `invalidateReadyGate()`（约 875 行）还会清理工作区视图并重新 bootstrap。这个事件不应该等同会话/空间失效。日志频率与之吻合，但持续刷新是否还有第二因素，修复时须用事件跟踪确认。
- **方案**：门禁只响应连接、凭据、空间纪元或明确的 `snapshot_invalidated`；伴星投递只刷新伴星/首页局部投影。相同账号+空间+epoch 的再次校验不清空页面。给 bootstrap 加同代请求合并和有限失败出口，显示能操作的重试，而不是无限 spinner。
- **验收**：连续投递 100 条伴星事件，当前学习页面和焦点不消失、`/auth/me` 不随事件数增长；真实断网/换空间仍正确收口；长时间等待超过阈值能看到明确状态和重试。

### F02 · P0 · 卡片生成恢复接口稳定 500

- **证据**：本地认证只读请求 `/v2/card-generation-runs/active` 返回 500（约 32ms），其余目标、复习、笔记、来源接口同时返回 200；API 日志重复 `ZodError`；库中有 10 个非终态生成 run。首页显示“恢复信息需要重新读取 1”。
- **确定根因**：`apps/api/src/modules/card-generation-v2/generation-run-service.ts:479` 使用 `rows.map(serializeRunPublic)`，而 `serializeRunPublic` 是 `async`（`helpers.ts:297`），因此把 `Promise[]` 交给 `routes.ts:150` 的 Zod 投影解析。
- **方案**：`await Promise.all(rows.map(...))`，保留批量算好的 `outdatedByRunId`；对非空列表和多个状态做路由级测试，断言 JSON 真正可序列化、状态 200、列表顺序正确。客户端 500 时提供显式重试与原因，不让恢复入口只剩模糊胶囊。
- **验收**：在 4 个 `needs_attention`、6 个 `review_ready` 的当前数据形状下返回 200；首页能打开对应恢复任务；空列表也返回 `[]`。

### F03 · P1 · 理解目标的进度、练习、正式验证、复习四种说法互相冲突

- **证据**：实机目标 `Earth's orbital period` 同屏出现“走到第 2 段：练过了”“0 次练习”“正式验证还没安排”“当前旅程等待下一步”“复习安排已经到期”，上次结果又是“本轮暂无法判定”。`objective-progress-band.ts:19-23` 把 `learning` 一律映射为“练过了”，只要 run 开始，即使练习次数为零。`WorkspaceLibrarySurface.tsx:690-706` 将多条独立状态并排输出，未解释它们是否属于同一轮、同一张卡。
- **方案**：将“是否开始本轮”“是否有练习记录”“是否有正式证明”“哪张卡何时复习”拆成明确范围，但页面只突出**当前可做的一步**。未提交任何练习时进度写“作答中”，不要写“练过了”；`0 次练习`保留。复习到期必须标出卡/排程范围，避免看上去与“正式验证未安排”矛盾。所有入口使用服务端同一 `primaryAction` 和同一原因文案。
- **验收**：覆盖新目标、run 刚开始、暂无法判定、已验证且到期、并行多张卡五组状态；任何一屏只出现一个主操作，进度词与真实记录不冲突。

### F04 · P1 · 同目标的复习卡无法区分

- **证据**：实机队列共 3 张，覆盖 1 个目标；前两张都是 `Earth's orbital period`，来源均为同一篇笔记，后续顺序也重复显示这个标题，只有“排期第 2/4 轮”和过期天数不同。`ReviewSurface.tsx:789-808` 的 `questionOf()` 只取目标 `conceptLabel/publicSummary`，`originOf()` 只取主笔记；没有卡级问题或练习目的。
- **方案**：复习单位若仍为卡，卡面和顺序按钮必须显示卡级可区分信息（问题摘要/类型/上次薄弱点 + 排程轮次）；若用户真正要做的是“复习一个目标”，则先按目标归组，再在目标内解释多卡顺序。选其中一个作为产品合同，避免“3 张卡却像重复同一件事”。建议**按目标归组，组内逐卡**，保留排程准确性。
- **验收**：同目标三卡在卡面、读屏名称、后续顺序中均能区分；开始后得到与卡面预告一致的问题。

### F05 · P1 · 目标简报的“主笔记”实际打开另一篇笔记

- **证据等级**：实机复现 + 代码可证。在非焦点目标 `IndexTTS 2.5 GRPO 后训练机制` 的卷宗中点“主笔记 IndexTTS 2.5 让声音跨越语言 - 哔哩哔哩”，实际打开 `E2E Test Note — Key Science Concepts`，属于另一目标的笔记。`WorkspaceLibrarySurface.tsx:725` 的按钮只 `invoke("open-notebook")`，不传所显示的 `primaryNote`；`room-store.ts:456-457` 保留旧 `activeNoteRef`，`notebook-surface.tsx:344-345` 无 ref 时又退到首页焦点目标的主笔记。
- **方案**：点击时先明确设置目标的 `noteId`/`noteVersionId` 再导航；找不到可用版本则禁用并解释。不要把首页焦点笔记当作任意入口的隐式回退。
- **验收**：从每个非焦点目标打开主笔记都落在对应 ID；先访问其他笔记再回来也不串；切空间后旧 ref 不复用。

### F06 · P1 · 补充证据题要求纠正“上次回答”，却不展示上次答了什么

- **证据**：实机进入既有 run 第 2 题，题面要求“指出上次回答中不准确或不完整的部分并纠正”，当前任务区仅展示通用题面和空白输入，没有紧邻可回看的上一答或具体缺口。目标简报只给“本轮暂无法判定”，不足以指导修正。
- **方案**：追问页固定一张简短“上一答 / 待补的具体点”卡，引用这次 run 的真实反馈；可折叠原答全文，避免泄漏标准答案。若服务端没有具体缺口，改成独立重述题，别命令用户纠正一个看不到的错误。
- **验收**：追问能指出本轮引用的原答 ID 与缺口；刷新、暂停后恢复仍能看到同一上下文；无缺口时不出现“纠正上次”的措辞。
- **第二轮补充（实机）**：这条已复现，并且比记录的更糟——追问本身也**注定失败**。本轮两题都提交后各得一次 `not_assessable`，第二次连“继续补充证据”按钮都消失了（`allowedFollowupIds` 变空）。原因见 F28：缺的是系统侧的冻结证据，不是用户的补充。

### F07 · P1 · worker 的 AI 外发审计日志写入失败

- **证据**：近 1 小时 worker 日志有 35 次 `failed to write AI audit log`；数据库最新审计行停在 9 月 22 日，9 月 23 日的伴星调用没有相应新行。`workers/ai-worker/src/lib/governance.ts:862-864` 默认直接 `db.insert(aiAuditLog)`。表上的 `sec01_v1_ai_audit_tenant_guard`、`insert_actor_guard` 要求 `app.workspace_id` 与 `app.user_id`，而 `ailearn_worker` 独立连接两项均为 NULL。日志另有模型提供方 503，那是独立故障，不是审计写不进去的解释。

- **键盘通路本身是好的（正控）**：同一个 `onEditorKeyDown` 里的 ⌘K 实测生效（我把光标停在字符“y”上按 ⌘K，正文里出现 `[y](https:)` 链接），所以 ⌘S 的无反应不能归给事件没送达，只能归给 `!dirty` 那道 return。
- **后果**：版本历史与“恢复切回那一版”这项能力，用户在正常写作节奏下**一次都触达不到**；F35 的“只有空 v1”正是它的直接产物。
- **方案**：把手动定版与 `dirty` 解耦——`save("manual")` 的语义是“把此刻定版”，内容没变时应该明确回“这已经是一个版本了”，而不是什么都不做；界面上把按钮名与提示语统一（要么都叫“提交并确认”，要么提示语改指“立即保存”），并让它常驻而不是只在 1.2 秒窗口里出现。⌘S 在无改动时也要给一句可读反馈。
- **验收**：正常写作停顿后仍能点一次按钮定出 v2；版本历史出现两条以上且“恢复”可用；提示语里的按钮名在屏上真实存在；⌘S 在无改动时给出明确回执而不是静默。

### F37 · P3 · “新建笔记”立刻落库成一篇空笔记，放弃也留在列表里

- **证据等级**：实机。点一次“新建笔记”（帮助文字是“新建一篇空笔记并直接开始写”）后，笔记计数从 13 变 14，新笔记当场以“无标题笔记 · 版本 v1”存在；我没写任何内容也会被记下来。配合 F35/F36，这类笔记永远停在“有版本、无内容”的形状，成为列表里的噪声（笔记库里已经能看到“无标题笔记”“测测测测测测测测测测测”这类残留）。
- **方案**：新建只在本地起稿，首次有内容自动保存时才落库；或保留即时落库但给“未完成的空白笔记”一条明确的清理入口（回收站已有删除路径，缺的是自动识别空稿）。
- **验收**：点开新建又直接离开，不增加笔记数；已有空稿能在列表里被一眼认出并批量处理。

## 4. 理解目标 → 复习：建议重排的产品合同

当前页面把**目标状态、某次 run、正式证据、卡片排程**放在同一平面上，且进度词使用“练过了/说清了”等结果语气。多个卡片属于同一目标时，复习队列又只显示目标标题，用户既不知道“现在做哪件”，也不知道“做完这件会改变什么”。

建议把用户可见流程固定为四步：

1. **材料与笔记**：从哪份材料形成了哪篇笔记，原文证据是否齐全。
2. **学习卡**：生成状态、候选要审什么、激活后有哪些卡，每张卡考什么。
3. **理解目标**：此目标当前的正式证据是什么；正在进行的是哪一轮作答。只给一个主按钮，如“继续第 2 题”，旁边解释“上次暂无法判定，需要补充 X”。
4. **复习**：按目标归组，显示该组共几张卡、各卡差别、今天先做哪张及原因；开始前区分“可正式结算”和“只能练习”，完成一张后立即说明目标状态与剩余排程如何变化。

目标简报的推荐结构：顶部“**你现在要做：继续补充证据（第 2/3 题）**”；其下独立三行“本轮作答：进行中”“正式证据：尚无可判定结论”“今天到期：2 张卡（来自此前激活的卡）”。进度条只表示**已完成**的步骤，不把“已经开始”算作“练过”。复习卡应有唯一可读名称，例如“轨道周期的因果解释 · 第 4 轮”，而不只重复“Earth's orbital period”。

服务端应提供一份可审计的 `nextAction`（动作、对象 ID、原因、阻断原因），首页、目标详情、今日学习和复习入口都按它展示，不各自猜下一步。并建立状态矩阵：新目标、只有练习、正式验证部分完成、暂不可判、已证明但待复习、同目标多卡到期、复习前曝光导致只能练习、材料过时、卡撤回。每一格明确唯一主操作、次级操作、返回目标和完成后的用户可见变化。

第二轮补完写入型链路后，这份合同要加一条**前置条件**，否则上面四步的第 2–4 步在真实数据上根本走不到：**一个目标只有在“每个必选评分点都有冻结证据”时才可以被激活成卡并进入复习**（F28）。当前实现把这条判断留在结算时刻，于是用户一路被允许走到“提交 → 判不出 → 补充 → 又判不出 → 结束但不改变复习”，队列回到原样，看起来像产品在原地打转。同理，材料侧要加一条：**采集失败必须表现为失败**（F27），否则第 1 步就断了却显示成“还在排队”，后面的笔记、卡、目标全都无从产生。这两条修好后，F03/F04/F06/F23/F24 的文案与入口收敛才有可验证的落点——否则状态矩阵里“暂不可判”那一格实际上吞掉了两种完全不同的原因。
