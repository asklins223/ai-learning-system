# v0.5 功能实现、Bug 修复与 UI 审核报告

- 审核日期：2026-07-20
- 审核对象：`codex/v0.5-implementation` 当前工作树
- 文档状态：终审记录（不代替测试、CI 或发布门禁结论）
- 审核重点：新增功能是否真实闭环、已修 Bug 是否修到根因、新增 UI 的信息架构、交互状态和响应式质量

## 1. 执行结论

v0.5 的主要产品链路已经形成，但审查初态不能认定为“除测试外均已完成”。初态至少存在以下真实实现问题：复习主提交会因契约冲突失败；start/submit 与 schedule 绑定、并发和幂等不完整；工作区切换会保留旧租户的客户端状态；onboarding 可被统计值和手动按钮误标；多人旧工作区会被错误复用为个人工作区；恢复数据可能破坏个人空间关系；设置和注册的新 UI 在手机端存在溢出、信息过载和交互状态不清的问题。

本轮已经直接修复上述可安全落地的问题，并把设置页、注册页、onboarding、复习提交与复习轨迹按同一套 **Learning Ledger / 学习台账** 视觉语言全量重绘。新的界面删去了英文装饰眉题、无意义序号、网格背景和多层嵌套卡片，把每个页面收敛到一个主要任务和一个明确下一步。修改后的 UI 已在桌面 `1440 × 1000`、手机 `390 × 844` 和暗色主题的真实浏览器页面中检查；核心页面无根级横向溢出，设置一次只显示一个分区，注册页不再裁切，邀请/成员表在手机端转为卡片行，危险操作使用可访问确认对话框。

当前结论分两层：

1. **功能与 UI 审核：有条件通过。** 注册、个人资料、多工作区、邀请/成员、onboarding、复习提交/稍后/历史等主链路已达到可继续联调的实现质量；本轮发现的主路径阻断已修复。
2. **生产发布：不批准。** `0027` 明确撤回了 `FORCE RLS`，运行时仍依赖应用层隔离；多人 legacy workspace 中的 user-private 数据尚未迁移到新个人空间；个人空间 pointer/owner membership 仍缺长期数据库约束。这些不是测试缺失，而是尚未完成的实现与安全设计。

## 6. 尚未解决的实现风险

### V05-RISK-01 · P0 · FORCE RLS 尚未完成

`0024_sec01_rls_enforce.sql` 对 24 张表执行 `ENABLE + FORCE ROW LEVEL SECURITY`，但更后的 `0027_sec01_rls_expansion_failsafe.sql` 又执行 `NO FORCE + DISABLE ROW LEVEL SECURITY`。这是为了让尚未全部使用 RLS transaction context 的 API/Worker 保持可运行，不是安全目标完成。

在完成运行路径改造、独立 security/data review 和新的前向 enforce migration 之前，跨 workspace 隔离主要依赖应用查询条件。若 v0.5 的生产要求包含数据库强制租户隔离，此项是发布阻断。

### V05-RISK-02 · P1 · 多人 legacy workspace 的 user-private 数据尚未迁移

0028 现在会为多人旧 workspace 的 owner/member 创建新的个人空间，但原 workspace 中的以下 user-private 数据尚未移动：validation events、review schedules/attempts、understanding events、evidence overrides 等。

这些记录引用原 workspace 的 card、key point、evidence 和 note version，不能只改 `workspace_id`，否则会制造跨 workspace 引用或在 RLS 启用后变成不可读。应先明确“复制依赖对象还是保留历史空间”的映射、冲突和回滚规则，再用独立迁移处理。当前数据未被静默搬错，但个人历史仍留在旧协作空间。

### V05-RISK-03 · P1 · 个人空间关系缺长期数据库约束

0028 在迁移末尾验证 pointer、workspace owner 和 active owner membership，但该校验只发生一次；`personal_workspace_id` 仍可为空，简单 FK 也不能保证 owner、workspace type 和 membership 同时成立。

正常注册、邀请注册、restore 和 join 路径已在事务中维护该关系，但未来 writer 或中断的 seed 仍可能写坏。建议采用可延迟的提交时 constraint trigger/复合 FK，或改造所有创建路径后再做 contract migration。

### V05-RISK-04 · P1 · started attempt 的跨页面/跨设备恢复尚未闭环

当前 UI 不再在取消前创建 attempt，且本页网络重试会保留 attempt/key；但服务端还没有“查询当前 started / abandon / 超时终止”能力。同一 schedule 使用不同 idempotency key 从多个页面或设备 start 时，仍可能产生多个 started，其中只有一个能完成。

建议增加“每 user + schedule 仅一个 active started”的持久约束和恢复端点，并为历史 started 定义过期/abandoned 状态。

### V05-RISK-05 · P2 · Review 结果来源追踪仍不完整

`review_attempts` 已预留 evidenceId/noteVersionId 等字段，但当前提交主要保存 validationQuestionId/keyPointId；next schedule ID 也只在响应中返回，没有持久绑定到 attempt。旧 attempt 在多轮复习后幂等回放时，可能只能按 subject 找到当前 pending schedule，而不是当时创建的那一条。

建议后续补充 nextScheduleId 和复习时的 evidence/note version snapshot，并用 workspace-aware 复合 FK 固化来源关系。
