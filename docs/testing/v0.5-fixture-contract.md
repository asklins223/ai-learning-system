# v0.5 测试 Fixture 契约

> Status: Accepted design；M1 实现<br>
> Owner: Quality Owner<br>
> Version: `v0.5-fixture-1`

## 目标

同一套 seed 协议供 PostgreSQL 集成测试、Playwright、双 Worker 故障测试和恢复演练使用。fixture 只能包含合成/公开样例，不包含真实 Alpha 用户内容或密钥。

## 确定性身份

fixture 每次运行生成独立 `runId`，所有 email、workspace slug 和 idempotency key 都包含该值；测试不能依赖数据库中“第一条”记录。

| 角色 | 必需状态 |
| --- | --- |
| Workspace A Owner | policy 已设置、Mock Provider、有效 session |
| Workspace A Member | policy 已确认、Mock Provider、有效 session |
| Workspace B Owner | 与 A 完全不同的内容和 session |
| Removed member | membership 已移除、旧 session 尚留待拒绝测试 |
| Invite fixtures | active、expired、revoked、consumed 各一条 |

## 业务对象

每个 workspace 至少有：

- 一篇 active note/version，包含标题、段落、代码块和长文本；
- 一张 active card 和一张 superseded card；
- hard、soft、rejected-by-current-user evidence 各一条；
- 服务端 validation question、understood/partial/misunderstood event；
- due、future、dismissed review schedule；
- 一个 pending、一个 retryable、一个 dead job；
- 51、100、1000 条边界集合只在 nightly/RC profile 创建。

Workspace A/B 使用形状相同但值不同的数据，以便任何跨 workspace 误读都会被断言发现。禁止使用 `null` 或相同正文让泄漏测试误通过。

## Seed 接口

实现应提供非生产可用的 CLI，而不是公开 HTTP 后门：

```text
seed --profile pr|nightly|rc --run-id <uuid> --format json
cleanup --run-id <uuid>
```

JSON 输出只返回测试所需 ID、一次性登录凭据和邀请明文 token；CI 必须将输出视为 secret artifact，不写普通日志。生产构建或 `NODE_ENV=production` 下 seed 命令必须 fail closed。

## 幂等与清理

- 同一 `runId` 重跑得到相同业务状态，不重复插入终态对象；
- cleanup 只删除带该 `runId` 的两个 workspace，拒绝空值、通配符和未知环境；
- 测试失败仍在 finally/CI post step 执行 cleanup；
- 恢复演练 fixture 不清理恢复目标，直到报告和 artifact 保存完成。

## 必需断言

- API/Worker 连接使用真实受限角色；
- 两 workspace 所有直接读写、关联、删除、搜索、导出都验证 0 泄漏；
- session/cookie/CSRF 通过真实登录路径取得，不手写绕过中间件；
- Worker 测试可控制时间、claim 顺序、lease expiry 与 late handler barrier；
- fixture schema version 必须进入 release test summary，版本不匹配时 readiness/E2E 失败。
